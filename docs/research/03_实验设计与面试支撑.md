# 实验设计与面试支撑（第一轮历史草案）

> 本文件保留第一轮 VHR-Opt 设计，不能直接作为当前实验或面试口径。当前方法已更新为 COVER-Opt，正式实验以 `../planning/05_工程实现任务计划.md` 为准；当前面试和简历表述以 `../../../06_技术岗位面试支撑材料.md` 为准。

## 1. 实验目标

实验必须回答三个质疑：

1. **不是只调用 LLM API**：证明完整方法优于 direct LLM / one-shot prompt。
2. **提升来源可解释**：证明 verifier、feedback、search、heuristic function 各自有贡献。
3. **优化结果可信**：证明输出满足硬约束，并能在小规模场景接近 oracle。

## 2. Baseline 设计

| 类别 | Baseline | 作用 |
|------|----------|------|
| 传统方法 | Random feasible | 最低参照 |
| 传统方法 | Latency-greedy | 看最短时延贪心能做到哪里 |
| 传统方法 | Load-balance greedy | 看资源均衡贪心能做到哪里 |
| 传统方法 | GA / NSGA-II | 与常见元启发式比较 |
| 求解器 oracle | MILP / CP-SAT small-scale | 小规模最优或近似最优参照 |
| LLM baseline | Direct LLM solution | 验证直接调用 LLM 的弱点 |
| LLM baseline | One-shot structured JSON | 区分自然语言输出和结构化输出 |
| 本文消融 | LLM + verifier, no repair | 看验证器本身作用 |
| 本文消融 | LLM + verifier + repair, no search | 看反馈修复作用 |
| 本文完整 | VHR-Opt solution search | 候选解搜索版本 |
| 本文完整 | VHR-Opt heuristic search | 启发式函数搜索版本 |

## 3. 指标矩阵

| 指标 | 解释 | 对应质疑 |
|------|------|----------|
| Feasible Rate | 生成候选通过硬约束的比例 | LLM 输出是否可信 |
| Constraint Violation Count | 平均约束违规数量 | verifier/repair 是否有效 |
| E2E Latency | 应用端到端时延 | 主优化目标 |
| QoS Violation Rate | 超过 QoS 阈值的比例 | 服务质量保证 |
| Resource Utilization | 节点和链路利用率 | 资源效率 |
| Load Balance | 利用率方差/Gini | 是否过载少数节点 |
| Migration Cost | 动态场景的迁移成本 | 动态适应能力 |
| Optimality Gap | 相对小规模 oracle 的差距 | 是否真在优化 |
| Planning Time | 搜索和验证耗时 | 工程可用性 |
| LLM Calls / Tokens | API 调用和成本 | 是否过度依赖 LLM |
| Repair Success Rate | 不可行候选经反馈后转可行的比例 | evaluate-and-refine 是否有效 |

## 4. 消融实验

建议至少做 8 组：

1. **Direct LLM**：自然语言描述后直接输出部署方案。
2. **Structured LLM**：要求输出 JSON，但不做 verifier。
3. **Structured + Verifier**：只过滤不可行候选，不反馈修复。
4. **Structured + Verifier + Repair**：加入 violation feedback。
5. **Heuristic Function + Skeleton**：LLM 生成评分函数，固定骨架执行。
6. **Heuristic + Verifier**：加入硬约束检查。
7. **Heuristic + Verifier + Elite Search**：加入候选池和精英选择。
8. **Full VHR-Opt**：加入多样性采样、违规反馈、动态场景测试。

## 5. 场景生成

### 小规模场景

用途：和 MILP/CP-SAT oracle 比 gap。

- 节点数：5-10。
- 服务数：5-15。
- 链路较稳定。
- 请求链较短。

### 中规模场景

用途：看搜索和启发式泛化。

- 节点数：20-50。
- 服务数：20-80。
- 多条服务链。
- 链路带宽和时延有扰动。

### 动态场景

用途：体现空间算力网络/卫星边缘的特殊性。

- 节点可用性变化。
- 链路时延或带宽突变。
- 请求热点迁移。
- 某些节点过载或失效。
- 约束中加入迁移成本。

## 6. 论文贡献写法

推荐写法：

```text
We propose VHR-Opt, a verifier-guided LLM heuristic refinement framework for microservice deployment in space computing power networks. Instead of directly trusting LLM-generated deployment plans, VHR-Opt maps natural-language deployment intents into a structured optimization IR, generates candidate solutions or executable heuristic functions, verifies hard constraints through a deterministic verifier, and iteratively refines candidates using violation-aware feedback and simulation-based objective scores.
```

贡献列表：

```text
1. We design a structured optimization intermediate representation for intent-aware microservice deployment, capturing compute resources, link states, service dependencies, QoS constraints, and dynamic migration preferences.

2. We propose a verifier-guided heuristic search pipeline that uses LLMs to generate candidate deployments or executable scoring functions while relying on deterministic verification and simulation to ensure feasibility and evaluate performance.

3. We introduce a violation-aware refinement mechanism that converts structure-side and solution-side verification failures into actionable feedback for iterative repair, improving candidate feasibility and search efficiency.

4. We conduct systematic experiments and ablations across static and dynamic network scenarios, comparing direct LLM generation, traditional heuristics, solver-based baselines, and variants of the proposed framework.
```

## 7. 面试答法

### 7.1 被问：这不就是调用 LLM API 吗？

答：

```text
如果只是把优化问题丢给 LLM 然后相信它的输出，那确实贡献很弱。我们后续强化的方向不是这样做，而是把 LLM 放在候选生成和启发式设计的位置。它生成的是结构化候选或局部评分函数，真正判断可行性的是约束验证器，判断好坏的是仿真器和目标函数。系统会把容量超限、路径不可达、QoS 超限等 violation report 反馈给 LLM，再做下一轮修复和搜索。所以 LLM API 只是生成模块，方法贡献在于验证器引导的搜索与反馈闭环。
```

### 7.2 被问：为什么不用传统优化算法？

答：

```text
传统优化算法仍然是必要的，我们没有放弃它。小规模场景可以用 MILP/CP-SAT 做 oracle，大规模场景用启发式和仿真评估。LLM 的价值主要在两个地方：一是把自然语言业务意图转成结构化约束，降低建模成本；二是生成多样的候选规则或启发式函数，帮助搜索跳出单一人工贪心策略。最后方案仍然要经过确定性验证和目标函数评价。
```

### 7.3 被问：怎么证明提升来自你设计的方法？

答：

```text
需要靠消融实验拆开看。我们会比较 direct LLM、structured LLM、加 verifier、加 repair、加 heuristic search、完整方法几组。如果只加结构化输出但没有 verifier，可行率可能仍然不稳定；如果加 verifier 但没有 repair，只能过滤不能改进；如果加 violation feedback 后可行率和目标值改善，就能说明反馈修复有效；如果 heuristic search 进一步降低目标值，就能说明搜索模块有贡献。
```

### 7.4 被问：LLM 生成的启发式代码安全吗？

答：

```text
第一版不让 LLM 生成任意系统代码，而是限制在固定函数签名和有限 API 里，例如 node_score 和 path_score。执行前做语法检查、禁止危险 import，运行时加超时和异常捕获。即使生成失败，也只是当前候选失效，不影响整个求解流程。这个设计参考了程序搜索类方法的思路：LLM 只演化关键逻辑，评估器负责筛掉不可执行或不可行结果。
```

### 7.5 被问：你们的方法有什么局限？

答：

```text
局限主要有三点。第一，LLM 生成质量受模型和 prompt 影响，所以必须用 verifier 和 evaluator 约束。第二，搜索带来额外 API 调用和规划时间，需要报告成本收益曲线。第三，当前方法更适合离线规划或准实时重规划，不适合毫秒级在线调度。我们会把这些作为边界条件写清楚，而不是声称 LLM 可以直接替代传统优化器。
```
