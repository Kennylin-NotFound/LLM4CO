# 相关工作方法地图：LLM 优化求解器

本文记录截至 2026-08-25 的第一轮调研结论。目标不是泛泛综述 LLM for optimization，而是提炼能用于当前论文拓展的技术机制：heuristic search、verification、evaluate-and-refine，以及 solver-in-the-loop。

> 状态说明：本文件中的 VHR-Opt/MCTS 建议属于第一轮方案。核对原论文并补充最新近邻工作后，当前主线已更新为 COVER-Opt；以 `../design/02_系统设计与方法论方案.md` 和 `../audit/04_方法论可行性与创新性审计.md` 为准。


## 1. 方法谱系

| 方向 | 代表工作 | 核心机制 | 对当前论文的启发 |
|------|----------|----------|------------------|
| 自然语言到优化模型 | [NL4Opt](https://arxiv.org/abs/2303.08233) | 将优化问题文本拆成实体识别和 meaning representation，再转为求解器可用格式 | 当前论文不能让 LLM 直接输出方案，应先生成结构化部署约束 |
| Solver-in-the-loop | [OptiMUS](https://arxiv.org/abs/2402.10172), [OptiMUS-0.3](https://arxiv.org/abs/2407.19633), [OptLLM](https://arxiv.org/abs/2407.07924) | LLM 负责建模、写代码、调试，外部求解器负责计算与反馈 | LLM 不是可信求解器，可信性来自优化器、验证器和执行结果 |
| 业务解释与 what-if | [OptiGuide](https://arxiv.org/abs/2307.03875) | LLM 接收自然语言查询，后端优化器回答定量 what-if 问题 | 论文可把 LLM 定位为需求理解和方案解释层，避免替代传统优化 |
| Evaluate-and-refine | [OPRO](https://arxiv.org/abs/2309.03409) | LLM 根据历史候选及其评分生成新候选，外部目标函数评价 | 当前部署问题可做“候选生成 - 仿真评分 - 反馈修复”闭环 |
| 程序空间搜索 | [FunSearch](https://www.nature.com/articles/s41586-023-06924-6) | LLM 生成可执行程序，自动 evaluator 筛选，程序数据库保留高分候选 | 不直接搜索部署解，而是搜索可解释的部署启发式函数 |
| 启发式自动设计 | [EoH](https://arxiv.org/abs/2401.02051), [MEoH](https://arxiv.org/abs/2409.16867), [LLM4AD](https://arxiv.org/abs/2412.17287) | LLM 生成启发式思想和代码，进化搜索保留高性能策略 | 可以把论文贡献升级为 LLM-assisted heuristic design |
| 双侧验证 | [Opt-Verifier](https://arxiv.org/abs/2605.29556), [VeriSimpl](https://arxiv.org/abs/2607.20474) | 从模型结构和求解结果两侧验证 LLM 生成的优化模型 | 当前论文可引入结构侧验证和解侧验证，解决“LLM 输出不可信” |
| 测试时搜索 | [SolverLLM](https://arxiv.org/abs/2510.16916) | 不训练模型，用 MCTS、结果反馈和不确定性回传提升求解 | 可作为进阶版本：用 beam/MCTS 控制候选搜索，而非单次 prompt |

## 2. 相关工作的共同规律

这些工作里，真正站得住的创新通常不在“用了哪个大模型”，而在下面几件事：

1. **中间表示**：把自然语言问题转成可检查的变量、约束、目标和数据结构。
2. **外部裁判**：用求解器、仿真器、测试用例或 verifier 判断结果，而不是相信 LLM。
3. **搜索空间约束**：不让 LLM 随意生成完整系统，而是让它生成候选解、局部规则、评分函数或 solver code。
4. **反馈闭环**：将错误、约束违规、目标函数值和历史高分候选反馈给下一轮生成。
5. **可消融实验**：比较 direct LLM、one-shot、with verifier、with repair、with search 等版本。

## 3. 对当前论文的直接结论

当前论文如果继续写“LLM Agent 求解微服务部署优化”，容易被问成：

- Agent 的状态是什么？
- 工具调用是什么？
- LLM 输出如何保证可行？
- 18% 提升来自 LLM，还是来自后端优化算法？
- 如果没有 LLM，传统启发式能否达到同样效果？

因此，论文拓展应把题目和方法收束为：

```text
Verifier-guided LLM Heuristic Search for Microservice Deployment in Space Computing Power Networks
```

中文可以表述为：

```text
面向空间算力网络微服务部署的验证器引导式 LLM 启发式搜索方法
```

这里的关键词含义要非常清楚：

- **LLM**：负责需求解析、候选策略生成、启发式函数生成和基于错误反馈的修复。
- **Heuristic Search**：搜索的是部署策略或启发式评分函数，不是一次性问答。
- **Verifier-guided**：所有候选都必须经过结构侧和解侧验证。
- **Microservice Deployment**：论文落点仍是空间算力网络中的服务部署、路由和资源约束。

## 4. 建议采用与暂不采用

### 建议采用

- 结构化中间表示：部署需求 DSL / JSON schema。
- 固定部署算法骨架：例如拓扑序部署、候选节点筛选、路径选择、资源更新。
- LLM 生成局部启发式：例如节点评分函数、服务排序规则、冲突修复规则。
- 外部验证器：容量、链路、时延、服务依赖、QoS、迁移代价。
- 反馈修复：将 violation report 和评分传回 LLM。
- 搜索控制：先用 beam / elite archive，后续可扩展 MCTS。

### 暂不采用

- 大模型训练、LoRA、RLHF、SFT：本轮明确排除。
- 复杂多智能体系统：除非有消融证明有效，否则容易变成包装。
- 让 LLM 直接输出最终部署结果：可作为 baseline，不应作为主方法。
- 过强理论保证：除非有证明，否则只说经验有效和验证可行。

## 5. 可写成论文 Related Work 的分类

后续写论文时可按三段组织：

1. **LLM for optimization modeling**：NL4Opt、OptiMUS、OptLLM。
2. **LLM-guided search and automatic heuristic design**：OPRO、FunSearch、EoH、LLM4AD。
3. **Verification of LLM-generated optimization artifacts**：Opt-Verifier、VeriSimpl、SolverLLM 中的 solver/evaluator feedback。

## 6. 第二轮补充结论

第二轮检索发现 FALCON 已覆盖 grammar constraint、feasibility repair 与 adaptive Best-of-N，Hercules 已覆盖 elite heuristic abstraction，DASH 已覆盖 dynamics-aware heuristic design 与 profile retrieval，CoEvo-AHD 已覆盖耦合子问题算子协同演化。与此同时，`Formalize, Don't Optimize` 指出 LLM 生成任意启发式可能牺牲正确性。

因此，当前方案不再把通用 verifier、elite archive、动态场景或任意 heuristic code generation 当作独立创新，而是聚焦：

1. Space-CPN 部署/路由有类型 DSL 与确定性执行骨架。
2. 约束-决策冲突图驱动的反例选择和定向 DSL patch。
3. 将原论文 solver-generation pipeline 作为可追溯 baseline，而非新版核心。

关键 gap 可以写：

```text
Existing LLM-based optimization methods either focus on generic mathematical modeling, natural-language interfaces to solvers, or program-level heuristic discovery. However, dynamic microservice deployment in space computing power networks requires jointly handling heterogeneous compute resources, time-varying links, service dependencies, and hard QoS constraints. Directly generated LLM solutions are difficult to trust, while conventional heuristics lack adaptability to high-level deployment intents. This motivates a verifier-guided LLM heuristic search framework that combines structured requirement parsing, executable heuristic generation, constraint verification, and simulation-based feedback.
```
