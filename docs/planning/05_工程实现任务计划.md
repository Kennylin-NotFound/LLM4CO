# COVER-Opt 工程实现任务计划

> 计划状态：approved for implementation  
> 本轮只完成计划，不创建实现代码  
> 估时为专注工作日，用于排序与控制范围，不是进度承诺

## 1. 工程目标

实现一套可复现的研究工程，能够回答以下问题：

1. 原论文 `Natural Language -> P/V/C/O -> Solver Code` pipeline 在统一 verifier 下到底能做到什么？
2. 有类型 DSL 和确定性执行骨架是否比直接方案/任意代码生成更可靠？
3. 约束-决策冲突图与定向 patch 是否比通用自然语言错误反馈更有效？
4. COVER-Opt 是否在固定 LLM/evaluator 预算下改善可行率、解质量或搜索效率？
5. 方法在动态链路与迁移场景中的收益、成本和失效边界是什么？

工程完成后应交付：

- 可运行源码与 CLI。
- 透明场景配置和固定随机种子。
- 原论文重建基线、传统基线和 COVER-Opt。
- 单元、集成、回归和属性测试。
- 可离线 replay 的 LLM 轨迹和完整 run manifest。
- 论文表格、图、统计、错误分析和案例。
- 只有在上述证据完成后生成的论文/简历/面试表述。

## 2. 不可破坏的设计约束

1. **确定性内核先于 LLM**：仿真、verifier、evaluator、oracle 和 baseline 未通过门禁前，不接入真实 API 搜索。
2. **解析与求解分离**：自然语言到 IR 的错误不能与优化算法质量混在同一主指标中。
3. **硬约束优先**：不可行方案不能依靠惩罚权重进入 feasible elite。
4. **LLM 只输出 DSL 或 patch**：核心方法不执行任意模型生成代码。
5. **统一裁判**：所有方法使用同一 PlanVerifier 和 ObjectiveEvaluator。
6. **固定预算**：搜索轮数、LLM calls、evaluator calls 和 wall time 由配置决定。
7. **全部可追溯**：提示、响应、解析、候选、计划、冲突和指标均持久化。
8. **允许负结果**：若核心机制无稳定优势，降级或修改贡献，不对结果进行叙事性包装。

## 4. 核心数据契约

### 4.1 ScenarioInstance

必须包含：

- `scenario_id`, `seed`, `time_slot`。
- node resources 与 compute rate。
- active links、distance、rate、bandwidth、availability window。
- service DAG、resource demand、workload、data volume、eligible nodes。
- QoS threshold、previous placement、migration budget。
- 参数来源与生成器版本。

### 4.2 DeploymentPlan

必须包含：

- 每个服务的唯一 placement。
- 每条依赖的 route。
- 分配后的节点/链路资源快照。
- 迁移列表。
- 构造状态：complete、partial 或 failed。
- 产生该计划的 method/candidate/run 标识。

### 4.3 VerificationReport

必须包含：

- `feasible`。
- 按类型分组的 violations。
- 每项 violation 的 magnitude、entities、contributing decisions。
- 对应 DSL components。
- verifier 版本。

### 4.4 HeuristicProgram

必须包含：

- DSL version。
- service order、node score、path score、repair policy。
- parent IDs 与 patch history。
- static verification 结果。
- AST signature，用于结构距离和去重。

### 4.5 RunManifest

必须包含：

- run ID、时间、命令、配置快照。
- Python/依赖版本、代码树 hash。
- 模型 provider/model/version/temperature。
- prompt hash、random seeds、budgets。
- 输入 scenario IDs 和输出 artifact paths。
- 成功、失败、重试、token 与 wall time 统计。

## 5. 分阶段实施

## Phase 0：研究契约冻结

**预计：1-2 天**

任务：

- 将 `../design/02_系统设计与方法论方案.md` 的符号与约束写入 `research_contract.yaml`。
- 固定首版问题范围：placement + deterministic route selection；不做联合双种群。
- 固定首版硬约束和主目标。
- 定义 claim-to-test matrix，所有结果字段先标记 `planned`。
- 建立参数来源表：原论文、公开资料、合成假设分别标注。
- 冻结旧“18%”为不可复用历史口径。

产物：

- `research_contract.yaml`
- `docs/problem_formulation.md`
- `docs/claim_test_matrix.md`
- `docs/parameter_provenance.md`

验收：

- 每个数学符号对应一个 schema 字段。
- 每个硬约束对应 verifier 条目和测试用例。
- 每个计划贡献至少对应一个消融。
- 不存在“等实验做完再定义”的主指标。

## Phase 1：工程骨架与可复现运行

**预计：1-2 天**

任务：

- 创建 `pyproject.toml`、包结构、CLI 和基础配置。
- 实现统一 seed 管理、日志、run manifest 和 artifact store。
- 实现 `MockLLM` 与 `ReplayLLM`，使 CI/本地测试不依赖 API。
- 建立 lint/test 命令和最小 smoke test。

计划 CLI：

```text
python -m cover_opt generate-scenarios --config ...
python -m cover_opt run-baseline --method greedy_latency --config ...
python -m cover_opt run-search --config ... --llm replay
python -m cover_opt evaluate --run-id ...
python -m cover_opt render-results --experiment ...
```

验收：

- 同一配置与 seed 生成相同 scenario hash。
- mock/replay 路径可跑通端到端空流程。
- 每次运行自动生成完整 manifest。

## Phase 2：Space-CPN 场景与仿真内核

**预计：3-5 天**

任务：

- 实现节点、链路、服务 DAG 和部署计划数据模型。
- 实现 Walker Delta 拓扑和时隙化节点位置/链路状态。
- 按原论文公式实现 processing、transmission 和 propagation latency。
- 实现微服务 DAG 生成器与固定 fixture。
- 实现 deterministic K-shortest feasible path 查询。
- 建立 small/medium/dynamic 三档场景配置。

关键测试：

- 同轨/异轨链路状态与距离变化的确定性测试。
- 单服务、链式 DAG、分叉/汇合 DAG 的手算时延测试。
- 不可达路径、带宽不足和窗口不足测试。
- 多前驱服务取最后到达时间测试。

验收：

- 手算场景的时延与代码一致。
- 同一 seed 的动态轨迹逐时隙一致。
- 场景可序列化并重新加载不丢字段。

## Phase 3：统一 verifier、evaluator 与小规模 oracle

**预计：4-6 天**

任务：

- 实现 unique placement、eligibility、capacity、connectivity、bandwidth、QoS、migration 验证。
- 实现端到端 latency、load imbalance、migration cost 和 planning time 指标。
- 使用 OR-Tools CP-SAT 实现小规模 placement oracle；节点间时延预计算。
- 实现随机小实例交叉检查和 property tests。
- 将原论文 Gurobi 依赖改为可选 adapter，主工程默认使用开源 CP-SAT。

关键测试：

- 每类约束至少包含一个合法和一个非法 fixture。
- verifier 对手工错误给出正确 entity 与 magnitude。
- CP-SAT 返回的可行解通过同一 PlanVerifier。
- 随机小实例中 verifier 与 oracle 的可行性判断一致。

Gate A：

- verifier、evaluator、oracle 未通过前，不进入真实 LLM 阶段。

## Phase 4：传统基线与原论文重建

**预计：3-4 天**

任务：

- 实现 Random Feasible、Latency Greedy、Balance Greedy。
- 实现一个标准元启发式 baseline；优先选择易于公平限制预算的 GA。
- 实现 `CurrentPaper-SolverGen`：自然语言/IR -> `P/V/C/O` -> solver model/code -> tests -> feedback。
- 实现 `DirectLLMPlan` 和 `StructuredLLMPlan` 作为弱基线。
- 重建 5 services/5 satellites 与 48/60/72 satellites 场景。

复现边界：

- 若没有原始代码、参数范围和 seeds，只能称为 `reconstructed baseline`。
- 先验证趋势与相对排序，不强行拟合论文柱状图数值。
- 所有基线统一使用相同 scenario instance、verifier 和 evaluator。

验收：

- 所有确定性 baseline 可批量运行。
- 小规模 exact baseline 的 gap 计算正确。
- 原论文重建报告列出已知一致项、重建假设和无法精确复现项。

## Phase 5：Typed DSL 与确定性执行骨架

**预计：4-6 天**

任务：

- 定义 JSON AST schema、白名单 feature/operator/repair action。
- 实现 DSL static verifier，不使用 Python `eval/exec`。
- 实现 service ordering、node scoring、path scoring。
- 实现 candidate mask、资源状态更新和 bounded repair/backtrack。
- 实现至少三个人工 heuristic：latency-first、capacity-first、migration-aware。
- 实现 AST canonicalization、hash 和 structural distance。

关键测试：

- 非法 feature、NaN/Inf、过深 AST、空规则、未知 action 均被拒绝。
- mask 过滤 eligibility 与局部 capacity。
- 三个人工 heuristic 在 fixture 上行为可解释、可重复。
- 同一 DSL/instance 输出完全一致。

Gate B：

- 三个人工 DSL heuristic 稳定运行并通过 verifier 后，才允许 LLM 生成 DSL。

## Phase 6：LLM 生成、缓存与回放层

**预计：2-3 天**

任务：

- 定义与 provider 无关的 `LLMProtocol`。
- 实现 OpenAI-compatible adapter、mock、replay 和 response cache。
- 设计 `generate full DSL`、`generic patch`、`conflict patch` 三类 prompt。
- 强制结构化输出并记录原始响应；解析失败不静默修补。
- 实现 token、latency、retry 和 failure 统计。

手工验证：

- 用一个代表场景测试模型是否能生成合法 DSL。
- 用一个 capacity conflict 和一个 QoS conflict 测试 patch 能否只修改允许组件。
- 将成功和失败响应保存为 regression fixtures。

验收：

- 缓存命中时不重复产生 API 成本。
- replay 可在无网络/无 key 情况下复现实验控制流。
- 模型切换不修改 search/verifier 代码。

## Phase 7：冲突图、反例选择与 COVER-Opt 搜索

**预计：5-8 天**

任务：

- 从 VerificationReport 构建 constraint-decision bipartite graph。
- 为 capacity、route、bandwidth、QoS、migration 实现 contribution attribution。
- 将冲突映射到 DSL components。
- 实现 generic feedback 与 conflict-directed feedback 两条路径。
- 实现 counterexample replay、candidate archive、AST diversity 和 budget controller。
- 实现结构 patch 应用、父子关系和失败回退。

关键测试：

- 人工冲突用例能够定位预期 decision 和 component。
- patch 不能修改未授权组件。
- 搜索在 call/eval/time 任一预算触发时确定终止。
- 搜索中断后可从 run artifacts 恢复。
- 被淘汰候选仍可追溯到原因。

预实验：

- 固定小场景和固定 10-20 次 LLM call budget。
- 比较 no feedback、generic text feedback、conflict-directed feedback。
- 观察 repair success、首次可行所需 calls、可行率和 objective。

Gate C：

- 若 conflict-directed feedback 没有稳定修复率或调用效率优势，暂停扩大实验，先审计 attribution 与 DSL 表达能力。

## Phase 8：动态滚动时域扩展

**预计：4-6 天**

任务：

- 实现时隙推进、链路变化、请求变化和节点资源扰动。
- 加入 previous placement、迁移成本、迁移预算和 fallback plan。
- 实现 rolling-horizon runner。
- 加入场景分割：开发场景、验证场景、最终测试场景。
- 评估 offline discovered heuristic 与 limited online refinement。

关键测试：

- 相同状态下保持原部署的 migration cost 为 0。
- 超预算迁移被 verifier 拒绝。
- 链路断开后受影响 route 被准确定位。
- refinement 失败时回退到上一可行计划或 deterministic baseline。

验收：

- 动态 episode 可逐时隙重放。
- 每个时隙均记录 plan、violations、迁移和规划耗时。
- 不使用“实时”字样，除非测得并定义明确 deadline。

## Phase 9：正式实验与统计

**预计：6-10 天，取决于 API 和求解预算**

### 9.1 开发与最终运行分离

- 开发阶段：少量场景和 3-5 seeds，用于排错。
- 最终阶段：计划 20 个独立 scenario seeds；若成本过高，需在看最终结果前锁定调整理由和新数量。
- 小规模 oracle、静态中规模、动态 episode 分开报告。

### 9.2 主 baseline

- Random Feasible。
- Latency Greedy。
- Balance Greedy。
- GA。
- CP-SAT small oracle。
- Direct LLM Plan。
- CurrentPaper-SolverGen。
- One-shot DSL。
- COVER-Opt full。

### 9.3 核心消融

- DSL without feasible masks。
- DSL + masks, no feedback。
- generic feedback。
- conflict feedback without counterexample replay。
- counterexample replay without component targeting。
- full COVER-Opt。

### 9.4 指标

- Feasible Rate。
- Constraint Violations by type。
- Objective / E2E latency。
- Optimality Gap on small instances。
- Repair Success Rate。
- Calls to First Feasible。
- Evaluator Calls。
- Planning Time 与 p95。
- LLM calls/tokens/retries。
- Dynamic QoS Violation Rate。
- Migration Count/Cost。

### 9.5 统计与可视化

- 报告均值与标准差；分布偏斜时补 median/IQR。
- 配对场景比较优先使用 paired tests 或 bootstrap CI。
- 同时报告绝对差异和相对差异。
- 不只展示最佳 seed。
- 主表之外必须有 failure type、cost-quality frontier 和 representative trace。

Gate D：

- 贡献、主结果、消融、成本、鲁棒性和错误分析全部有对应真实 artifact。
- 结果表可从一条命令重新生成。

## 6. 贡献到实现的严格对齐

| 论文主张 | 代码责任 | 首个门禁 | 最终证据 |
|---|---|---|---|
| typed heuristic search reduces generation failures | `heuristics/*` | Gate B | direct/raw/DSL 执行与可行率对比 |
| conflict graph enables targeted refinement | `verifier/conflict_graph.py`, `search/refiner.py` | Gate C | generic vs targeted feedback 消融 |
| counterexample replay improves search efficiency | `search/counterexamples.py`, `search/controller.py` | Gate C | calls-to-feasible、repair success、objective curve |
| method handles dynamic deployment trade-offs | `simulator/dynamic.py`, `evaluation/*` | Gate D | dynamic QoS、migration、planning time |
| results are trustworthy and reproducible | `storage/*`, configs, tests | Gate A-D | manifests、seeds、replay、one-command tables |

任何未映射到代码和实验的句子，不进入 contribution list。

## 7. 里程碑与优先级

### M1：可信确定性内核

包含 Phase 0-3。完成后即使没有 LLM，也应能生成场景、运行 baseline、验证计划和计算 oracle gap。

### M2：原论文可解释复现

包含 Phase 4。完成后可以准确解释原论文贡献、性能来源和证据缺口。

### M3：静态 COVER-Opt MVP

包含 Phase 5-7。它是论文方法的最小可发表核心；如果该里程碑失败，不应继续堆动态模块。

### M4：动态论文版本

包含 Phase 8-9。用于支撑 Space-CPN 场景特异性、迁移权衡和最终实验。

### M5：外部表述

包含 Phase 10。面试和简历材料最后更新，不与实现并行抢跑。

## 8. 最小技术栈

首版建议仅使用：

- Python。
- Pydantic 或等价 schema 校验。
- NetworkX 处理 DAG、卫星图和候选路径。
- NumPy 进行确定性数值计算。
- OR-Tools CP-SAT 作为小规模 oracle。
- pytest 进行测试。
- pandas/matplotlib 或等价工具聚合结果与出图。
- 一个 OpenAI-compatible LLM adapter，加 mock/replay。

不需要 LangChain/LangGraph、向量库、Kubernetes、ns-3 或数据库。它们不能帮助验证本论文的核心假设，首版加入只会增加依赖和叙事噪声。

## 9. 主要风险与应对

| 风险 | 早期信号 | 应对 |
|---|---|---|
| 无法精确复现原论文 | 参数/seed/代码缺失 | 明确 reconstructed baseline，保留假设和差异表 |
| DSL 太窄 | 人工 DSL 明显弱于 greedy/GA | 扩展 feature/operator，但仍保持白名单和静态验证 |
| 冲突定位不准 | targeted feedback 反而降低修复率 | 先修 attribution fixture，不扩大搜索预算 |
| LLM 贡献不稳定 | 不同 seeds/model 波动大 | 报告分布和模型敏感性，降低通用性主张 |
| API 成本高 | 重复响应或 evaluator 浪费 | cache、replay、去重、分阶段 scenario batch |
| CP-SAT 过慢 | medium case 超时 | oracle 限定小规模，大规模只比较可行 heuristic |
| 动态规划过慢 | 超过时隙 deadline | 限定 offline/quasi-real-time，使用已发现 heuristic 和 fallback |
| 最新工作重叠 | 投稿前出现相同机制 | 投稿前复检；根据结果收缩 novelty 或更换主张 |
| 结果只在训练场景有效 | test scenarios 明显退化 | scenario split、counterexample overfitting 分析、降级泛化主张 |

## 10. Definition of Done

工程只有同时满足以下条件才算完成：

- [ ] Phase 0-10 的产物均存在，或明确记录被取消的理由。
- [ ] 全部自动测试通过，关键约束有合法/非法双向用例。
