# COVER-Opt 完整管线与方法论验收说明

## 0. 验收结论

COVER-Opt 当前可以被验收为一套完整、可运行、可解释的 **可验证 LLM 优化求解系统**。它不是让大模型直接给出最终部署答案，也不是把大模型生成的代码直接执行，而是把 LLM 放在受限的策略搜索环节：

```text
固定起点 + 可选 LLM typed DSL 多起点
  -> 静态验证、去重与确定性择优
  -> LLM 提出局部启发式 Patch
  -> 静态合同与权限检查
  -> 确定性执行器生成部署/路由方案
  -> 统一验证器检查硬约束
  -> 目标评估器评价可行候选
  -> 控制器接受、回滚、探测或终止
```

从方法论上，它回答的是：**如何利用 LLM 的语义判断能力探索优化启发式，同时把精确计算、约束裁决、候选接受和停止条件交给可复现的确定性模块。**

从工程上，它已经覆盖输入合同、策略表示、候选生成、执行、验证、评价、反馈、搜索、记忆、预算、缓存、回放、恢复、统计和命令行入口。当前最合适的对外定位不是“自主通用 Agent”，而是：

> Verifier-guided LLM optimization system with a bounded agentic refinement loop.

中文可表述为：

> 采用有界反馈搜索的可验证 LLM 优化求解系统。

## 1. 问题与设计目标

### 1.1 输入与输出

系统处理带有服务依赖、异构资源和网络约束的微服务部署问题。一个场景包含：

- 计算节点及 CPU、内存、处理能力等资源。
- 网络链路及连通性、传播时延、带宽和可用窗口。
- 微服务 DAG、服务资源需求和依赖数据量。
- 上一时刻部署、迁移预算和 QoS 阈值。
- 时延、负载均衡和迁移成本等软目标权重。

输出是部署与路由计划：

```text
Pi = (X, R)
```

- `X`：每个微服务对应的部署节点。
- `R`：每条服务依赖对应的网络路径。

### 1.2 设计目标

系统同时满足四个目标：

1. **可行性可信**：LLM 不能自行宣布方案可行，所有候选由统一验证器裁决。
2. **搜索可控**：模型只能在受限动作空间内修改启发式，调用次数和 evaluator 次数有硬预算。
3. **结果可归因**：区分 LLM 的结构建议、确定性执行、数值探测和最终目标改善。
4. **过程可复现**：保存 Prompt、响应、配置、哈希、轨迹、成本和停止原因，支持 Replay 与续跑。

## 2. 为什么需要 LLM，也为什么不能让 LLM负责全部求解

微服务部署同时涉及服务拓扑、资源竞争、网络路径、QoS 和迁移等耦合因素。确定性算法擅长精确计算和约束检查，但手工设计一个能适应不同冲突模式的启发式较为困难；LLM 擅长根据结构化语义判断“哪一类决策规则可能导致当前失败”，适合提出局部策略修改。

因此系统采用职责分解：

| 工作 | 负责模块 | 原因 |
|---|---|---|
| 理解违规与决策之间的语义关系 | LLM Patch Generator | 需要上下文判断和策略组合 |
| 选择应修改的 DSL 组件或特征 | LLM Patch Generator | 属于离散结构探索 |
| 生成可选完整 DSL 起点 | LLM Heuristic Generator | 扩大受限搜索的初始覆盖范围 |
| 构造部署和路由 | Deterministic Executor | 需要稳定、可重复执行 |
| 检查硬约束 | PlanVerifier | 需要单一可信裁判 |
| 计算目标值 | ObjectiveEvaluator | 需要精确、统一口径 |
| 搜索局部权重 | Counterfactual Probe | 小规模数值搜索更适合确定性枚举 |
| 接受、回滚和停止 | SearchController | 不能由随机模型自行越过预算和门禁 |

核心判断是：**LLM 是策略结构生成器，不是可行性裁判，也不是数值优化器。**

## 3. 总体架构


## 4. 核心数据合同

### 4.1 ScenarioInstance

`src/cover_opt/domain/models.py` 使用严格 Pydantic 模型描述节点、链路、服务、服务依赖、上一部署和优化约束。模型禁止额外字段，并检查引用关系与服务 DAG，避免错误输入在后续阶段静默传播。

### 4.2 HeuristicDSL

`src/cover_opt/heuristics/schema.py` 把启发式拆成四个组件：

| 组件 | 作用 |
|---|---|
| `service_order` | 决定服务的处理顺序 |
| `node_score` | 对候选部署节点评分 |
| `path_score` | 对候选网络路径评分 |
| `repair_policy` | 指定有界确定性修复动作 |

每个评分规则都是有限项 `weighted_sum`。特征和 repair action 来自枚举白名单，权重必须是有限数值，表达式规模受限。这使 DSL 具备可执行、可比较、可哈希和可静态检查的性质。

### 4.3 HeuristicPatch

LLM 不重写整个 DSL，而是输出 `src/cover_opt/heuristics/patch.py` 定义的局部操作：

- `set_weight`
- `add_term`
- `remove_term`
- `set_direction`
- `set_repair_policy`

每个 Patch 最多 8 个操作。`AuthorizedPatchApplier` 同时检查目标组件、评分特征和 repair action 是否被当前冲突授权，随后重新运行 DSL 静态验证。越权、未知特征、重复添加和删除不存在项不能进入执行器；结构上合法但语义重复或行为无效的修改由后续语义去重与 outcome gate 拒绝。

### 4.4 VerificationReport 与 ObjectiveReport

验证结果和目标结果是两个独立合同：

- `VerificationReport` 表达可行性、违规类型、幅度、实体和数值贡献。
- `ObjectiveReport` 只为已验证可行的候选计算时延、负载、迁移成本和加权目标。

这保证硬约束不会因为加权目标较低而被“抵消”。

## 5. 确定性执行与约束验证

### 5.1 执行骨架

`src/cover_opt/heuristics/executor.py` 将 DSL 转换为实际计划：

1. 计算服务特征并按 `service_order` 排序，同时保持 DAG 依赖合法。
2. 为当前服务生成可部署节点集合。
3. 启用 feasible mask 时，提前过滤资格或容量不满足的节点。
4. 按 `node_score` 对剩余节点排序并选择部署位置。
5. 为服务依赖生成 top-k 候选路径。
6. 启用 feasible mask 时，过滤不可用、窗口不满足或共享链路剩余带宽不足的路径，并在选择后扣减本时隙容量。
7. 按 `path_score` 选择路径。
8. 根据 `repair_policy` 执行有界 reroute、move、swap 或 backtrack。
9. 输出计划、失败原因、规划耗时和逐阶段 trace。

相同场景和相同 DSL 在确定性内核中得到相同执行结果，便于归因 Patch 的真实作用。

### 5.2 七类硬约束

`src/cover_opt/verifier/plan_verifier.py` 是系统唯一的可行性裁判，检查：

1. 每个服务恰好部署一次。
2. 节点部署资格。
3. 计算与内存容量。
4. 路由连通性。
5. 链路带宽。
6. 端到端 QoS 时延。
7. 迁移预算。

每个违规携带 `violation_type`、归一化幅度、相关实体、贡献决策和 `attribution_method`，而不是只有一段自然语言错误。节点资源、共享流量和迁移事件可按实际份额归因；QoS 当前使用明确标记的代理归因。PlanVerifier 会重新聚合所有路由在同一物理链路上的时隙带宽需求，避免单流均合法但总和超限。

## 6. 冲突图与反例反馈

### 6.1 约束-决策冲突图

`src/cover_opt/verifier/conflict_graph.py` 把验证报告转换成约束-决策二部图，并生成对应授权集合：

- 约束节点：哪一类硬约束失败。
- 决策节点：涉及哪些服务、节点、链路或路径。
- 授权集合：哪些 DSL 组件、评分特征和 repair action 可以进入当前修复邻域。

映射由确定性规则维护。例如：

- 迁移预算主要关联 `node_score` 和 `repair_policy`。
- 路由连通性与带宽主要关联 `path_score` 和 `repair_policy`。
- QoS 同时可能关联部署顺序、节点选择、路径选择和修复策略。

因此，LLM 接收到的不是泛化的“结果不可行”，而是受约束的因果候选范围。

### 6.2 反例记忆

`src/cover_opt/search/counterexamples.py` 按场景哈希、违规类型和相关实体聚合反例，记录：

- 出现次数。
- 最近候选与 AST 签名。
- 冲突图签名。
- 修复失败次数。
- 已重放次数和最近重放轮次。
- 重放优先级。

它不是自由文本长期记忆，而是结构化失败模式档案。`search/replay.py` 会在总重放预算和单反例次数上限内选择高严重度、高频、反复修复失败且尚未过度重放的反例，再由候选档案选择违规负担较低的可修复父策略。该选择会写入 trajectory，而不是只在返回值中保留一个未消费队列。

重访只能在至少一次修复失败后触发。若子候选在结果门禁中被拒绝，它会保留于轨迹供审计，但 `expansion_eligible=false`，不得绕过回滚再次成为父候选。

### 6.3 跨运行场景重放

`src/cover_opt/search/campaign.py` 将反例记忆提升到 campaign 级：

- seed run 失败后保存完整 `ScenarioInstance`、结构化反例、合格父 DSL、来源运行和父候选。
- 外层调度按修复失败数、观测频次、违规类型数和负担选取任务。
- scenario replay 创建新的 `SearchController` 运行，而不是继续伪装成原运行的下一轮。
- CLI 产物同时落盘场景快照、来源、重放轨迹、解决状态与预算统计。

这支撑“受控 campaign 内跨求解运行的失败场景重放”。它不等同于已部署跨进程、跨用户的在线长期记忆服务。

## 7. LLM 候选生成

### 7.1 可选完整 DSL 初始化

`src/cover_opt/llm/heuristic_generator.py` 可在固定数量内生成完整 typed DSL 起点。模型只能使用 operator catalog 中的四类规则，输出先经过 schema、重复项、有限权重和场景静态检查，再按 AST 签名去重。SearchController 将固定起点与有效生成起点交给同一个 executor/verifier/evaluator；若存在可行候选则按目标值选择，否则按违规负担选择可修复候选。默认冻结协议仍可只使用固定起点。

初始生成不是预算外的免费步骤。控制器将初始 DSL 生成和后续 Patch 生成分别记为 `initial_generation_calls` 与 `patch_generation_calls`，并由 `total_llm_calls` 共享总上限。调用后端失败或生成非法结构同样消耗调用预算。

### 7.2 局部 Patch 生成

`src/cover_opt/llm/patch_generator.py` 将 `RefinementContext` 渲染为版本化 Prompt，并要求模型返回严格 JSON。上下文包含：

- 当前场景摘要。
- 父 DSL。
- 当前验证结果或目标分解。
- 冲突图和允许修改的组件、特征与 repair action。
- operator catalog 与 Patch affordance。
- 既往被拒 Patch 及拒绝原因。
- 已尝试但未改善的目标 Patch。
- 单次 Patch 操作上限。

模型响应依次经过 JSON 解析、Pydantic schema、操作语义、组件权限和 DSL 静态检查。任何一层失败都会形成结构化拒绝反馈，但不会改变当前 incumbent。

## 8. 搜索控制循环

### 8.1 状态

`SearchController` 维护的状态包括：

- 当前场景与初始 DSL。
- 当前候选和最佳可行候选。
- 候选档案与结构签名。
- 当前反例和反例历史。
- 被拒 Patch 与未改善目标 Patch。
- 初始生成、Patch 生成与总 LLM 调用账本，evaluator 和 wall-time 预算。
- 完整 trajectory 与停止原因。

### 8.2 主循环

```text
validate and deduplicate(fixed DSL + optional generated DSLs)
evaluate and archive(initial candidates)
select best feasible or lowest-burden repairable parent

while budget remains:
    if stopping condition is met:
        break

    optionally schedule a bounded counterexample replay after repair failure
    select its repairable parent from the archive
    context = build_context(current candidate, verifier/evaluator feedback)
    patch = LLM.propose(context)

    if parse/schema/authorization/static check fails:
        remember rejection
        continue

    child = deterministic_execute(parent + patch)
    report = verify(child)

    if feasibility phase and child does not improve violations:
        reject outcome and rollback
        optionally probe bounded numeric counterfactuals
        continue

    if objective phase and objective does not improve:
        rollback to incumbent
        optionally probe bounded numeric counterfactuals
        continue

    archive(child)
    update current/incumbent/counterexample memory

return best feasible candidate, trajectory, statistics, stop reason
```

### 8.3 结果感知拒绝

系统不会把“AST 发生变化”直接视为搜索进展。控制器构造 behavior signature，包含：

- 实际 placement。
- 实际 routes。
- 违规类型、幅度和相关实体。

在可行性阶段，子候选必须满足：

- 直接变为可行；或
- 不引入新的违规类型；且
- 现有违规不变差；且
- 至少消除一种违规或降低某个违规幅度。

否则 Patch 被 outcome rejection，控制器回滚到父候选，把子候选标记为不可扩展，并将“行为未变化”或“违规未改善”的原因反馈给下一轮。这一机制直接阻止模型通过无效改权重消耗全部预算，也防止 replay 绕过回滚门禁。

## 9. 语义-数值混合优化

LLM 对“应该修改哪个组件、哪个特征”有语义优势，但对精确权重符号和幅度不稳定。`src/cover_opt/search/probes.py` 因此采用职责分解：

1. LLM 选择一个局部组件或特征。
2. 如果候选在结果层无改善，deterministic probe 在同一组件内生成有限反事实权重。
3. 每个 probe 仍占用 evaluator 预算并经过同一执行器、验证器和目标评估器。
4. 第一个严格改善的 probe 可成为新 current；无改善则保留原 incumbent。

这不是让程序替代 LLM，而是将离散语义搜索与小范围数值搜索分开，使两类模块各自承担更适合的任务。

## 10. 候选档案与停止条件

`src/cover_opt/search/archive.py` 保存所有候选及父子关系、AST 签名、执行结果、验证结果、目标值和冲突图。档案支持：

- 最优可行候选选择。
- 反例重放时的可修复父候选选择。
- 相同 AST 去重。
- 结构多样候选的 deterministic farthest-first 选择。

控制器可因以下条件停止：

- 初始候选已满足目标阶段要求。
- 达到首个可行解且配置要求停止。
- Patch generator 无候选。
- 总 LLM 调用预算或 Patch 提案预算耗尽。
- evaluator 预算耗尽。
- wall-time 预算耗尽。

模型不能自行延长预算或绕过停止条件。

## 11. 工程实现设计

### 11.1 Provider 解耦

`LLMProtocol` 统一 Mock、Replay 和 DeepSeek 后端。搜索控制器只依赖 `propose(context)`，不依赖特定 API。这样可以：

- 使用 Mock 验证最小流程。
- 使用 Replay 在无网络条件下重放真实结构化轨迹。
- 使用 DeepSeek 验证在线模型行为。
- 在不改搜索内核的情况下替换模型提供方。

### 11.2 在线调用边界

`src/cover_opt/llm/deepseek.py` 实现：

- API Key 只从环境变量读取。
- 官方 HTTPS host 白名单。
- 请求与响应 fingerprint。
- JSON object 解析与空输出、截断拒绝。
- 408/409/429/5xx 有界重试。
- system fingerprint 漂移检查。
- 输入/输出 token、缓存命中和延迟记录。

### 11.3 缓存、原子落盘与恢复

- LLM 响应按请求 fingerprint 和模型配置缓存。
- 每个实验 run 使用独立 run key，避免重复运行混淆。
- 运行记录先写临时文件再原子替换。
- Resume 时核对 protocol、config、source tree 和 scenario hash。
- 已完成 run 不重复计费；不一致的旧 artifact 会被拒绝续跑。

### 11.4 成本与故障门禁

正式 runner 在运行前计算最坏 token 成本，超过配置上限则拒绝启动；运行中累计实际估算成本，越过门限时终止。provider failure、schema failure、cache usage 和 system fingerprint 分开记录，不把基础设施失败混成算法不可行。

## 12. Agent 称谓审计

### 12.1 系统是否具备 agentic loop

| Agent 要素 | 当前实现 |
|---|---|
| Environment | 场景、确定性执行器、验证器和 evaluator |
| State | DSL、候选、反例、拒绝历史、档案和预算 |
| Observation | VerificationReport、冲突图、objective 分解和 trace |
| Action | 有类型 `HeuristicPatch` |
| Memory | counterexample archive、Patch rejection history、candidate archive |
| Policy | LLM 根据上下文提出局部 Patch |
| Feedback loop | Patch 后重新执行、验证、评价并更新状态 |
| Termination | 首个可行、预算、无候选、wall time 等确定性门禁 |

因此，**整个系统具有有界 agentic refinement loop**。

### 12.2 为什么不建议直接称“自主 LLM Agent”

严格的现代 LLM Agent 叙述通常暗示模型自行规划、选择工具、决定下一步并在一定范围内控制循环。COVER-Opt 中：

- LLM 只选择一个受限 Patch 动作。
- LLM 不直接调用 executor/verifier/evaluator。
- LLM 不决定候选是否接受。
- LLM 不决定预算与最终终止。
- 工具编排由确定性 SearchController 完成。

所以最稳妥的称谓是：

1. **首选：可验证 LLM 优化求解系统。**
2. **技术说明：带有有界 agentic refinement loop 的 LLM-in-the-loop solver。**
3. **可在解释后使用：bounded optimization agent / solver agent。**
4. **不建议：自主 LLM Agent、多智能体优化系统、具备自主工具调用的 Agent。**

是否使用“Agent”不是项目强弱的判断。研究价值来自受限策略表示、确定性验证反馈和搜索机制，而不是名称中必须出现 Agent。

## 13. 方法技术特点与合理性

### 13.1 有类型启发式算子空间

将搜索对象从完整方案或任意代码收缩为局部 DSL Patch，使模型输出可静态验证、可授权、可执行、可比较和可回放。这是可靠性的来源之一。

### 13.2 冲突定向的局部反馈

验证器输出不仅指出约束失败，还把失败关联到具体决策和可能相关的 DSL 组件。这样模型处理的是压缩后的局部搜索问题，而不是重新生成整个求解器。

### 13.3 结果感知的候选接受

系统以实际 placement、route、violation 和 objective 判断进展，不以 Prompt 文本或 AST 变化判断成功。该机制使“模型输出合法”与“求解行为有效”成为两个独立门禁。

### 13.4 语义-数值职责分解

LLM 负责结构和因果方向，确定性 probe 负责小范围数值邻域。所有 probe 共用预算与 verifier/evaluator，因此不会形成隐藏的免费搜索。

### 13.5 单一确定性裁判

传统基线、LLM 方案和 COVER-Opt 候选共享 PlanVerifier 与 ObjectiveEvaluator，降低比较时因评价实现不同产生的偏差。

这些特点构成一套能讲通的方法论：每个模块都对应一个具体失败风险，模块之间存在清晰的输入输出和控制关系，并能通过 feature switch、轨迹与测试分别验证。

## 15. 严格论述边界

### 15.1 可以直接声称

- 设计并实现了完整的可验证 LLM 优化求解管线。
- LLM 可生成受限完整 DSL 起点和有类型局部 Patch，最终计划始终由确定性执行器生成。
- 系统使用统一验证器检查 7 类硬约束。
- 实现了特征级冲突反馈、失败后反例重访、受控 campaign 内跨运行失败场景重放、候选父策略选择、预算控制、重复拦截和结果感知回滚。
- typed DSL 初始生成与 Patch 生成共享总 LLM 调用预算，失败调用也进入账本。
- 实现了 LLM 结构选择与确定性数值 probe 的混合 refinement。
- 系统支持 Mock、Replay、DeepSeek、缓存、指纹、成本统计和可续跑 artifact。
- 106 项自动测试通过；v1.3 受控 runner 完成 440/440 个记录且基础设施失败为 0。新增机制的六变体离线消融和跨运行 replay campaign 只作为控制流证据。

### 15.2 需要加限定后声称

- “Agent”：应限定为“有界 agentic refinement loop”或“bounded solver agent”，并说明控制器掌握工具与终止。
- “最优”：只能说 exact enumeration 在当前有限放置与 top-k 路径候选集合内证明最优。
- “性能改善”：只能引用具体受控场景与具体运行，不外推为普遍优势。
- “动态算网”：问题合同和场景生成支持时间与上一部署状态；完整滚动时域验证应作为 further work 说明。

### 15.3 不应声称

- 自主通用 LLM Agent 或多智能体系统。
- LLM 自主选择和调用外部工具。
- 已进行模型训练、微调或强化学习。
- 已部署到真实 Kubernetes 或卫星网络生产环境。
- 已证明全局最优、方法普遍显著优于所有基线或可直接泛化到大规模生产实例。
- 具有未经测试的实时性、稳定性或理论保证。

## 16. 最终验收判断

从研究型技术项目的角度，COVER-Opt 不需要为了“像 Agent”而加入多智能体、自由工具调用或模型训练。当前方法论的完整性来自：

```text
清晰问题定义
  + 受限且可执行的策略表示
  + LLM 参与的局部结构搜索
  + 确定性执行与统一验证
  + 反例反馈和结果感知修复
  + 有界预算、回滚、回放和证据链
```

这已经能够覆盖技术岗位通常关心的方法合理性、LLM 的实际作用、可靠性设计、工程可复现性、失败处理、评估意识和个人实现深度。对外应强调这套职责分解和闭环设计，而不是追求更大的技术名词集合。
