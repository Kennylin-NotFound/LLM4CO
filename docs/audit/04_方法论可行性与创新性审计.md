# 方法论可行性与创新性审计

## 1. 审计结论

结论：方法可实现，但原 `VHR-Opt` 不能直接作为最终论文方案。`verification + evaluate-and-refine + elite search` 已被多个近邻方向覆盖，若只在 Space-CPN 上组合这些模块，创新性仍偏应用型。

当前工程已按 `COVER-Opt` 主线完成核心机制，创新焦点压缩为三个彼此可消融的算法设计：

1. 面向部署/路由决策的有类型启发式 DSL 与确定性执行骨架。
2. 从约束违规到具体决策、归因口径、DSL 特征和修复动作的冲突图驱动反例修复。
3. 候选档案参与的有界反例重放，以及固定/LLM typed DSL 多起点的统一择优。

动态滚动时域和完整评估协议作为问题/证据贡献，不单独声称通用算法首创。

## 2. 原论文审计

### 2.1 已经真实存在的能力

- 自然语言到 `P/V/C/O` 的结构化建模。
- RAG 辅助模型整合。
- 预定义模板生成 Gurobi MIP 代码。
- 本地测试、执行错误和建模错误分类反馈。
- Walker Delta LEO 场景、微服务 DAG、资源与时延建模。
- Random、Greedy、Branch-and-Bound 和 LLM-generated solver 对比。

因此，面试时将原论文说成“只把问题丢给 ChatGPT 让它直接给答案”并不准确。更准确的批评是：原论文没有充分证明闭环中哪些模块产生了价值。

### 2.2 关键薄弱点

| 风险 | 原论文表现 | 对新版的要求 |
|---|---|---|
| 贡献归因 | LLM 方法最终使用 MIP solver，结果接近 optimal | 将 solver generation 单列为 baseline；优化搜索用相同 evaluator 比较 |
| Agent 证据 | 没有状态、动作、工具轨迹、预算或终止实验 | 新版标题不依赖 Agent；如后续使用该词，必须保存轨迹并做控制循环评估 |
| 动态性 | 只比较 48/60/72 星规模 | 引入时隙、链路变化、上一部署、迁移代价和动态 QoS |
| 可靠性 | 只描述 self-correction | 统计解析成功率、执行成功率、可行率、修复轮数和失败类型 |
| 实验公平性 | baseline 细节、随机种子、重复次数、运行时间不完整 | 固定实例、预算、随机种子；报告均值、方差/区间和成本 |
| 模型完整性 | 缺少显式路由、带宽、QoS、迁移约束 | 新版 verifier 与动态问题定义显式覆盖这些约束 |
| RAG 贡献 | 使用但没有独立数据集和消融 | 降级为可选基础设施，不进入贡献列表 |
| 18% 口径 | 原图不直接支持 LLM 相对 heuristic 改善 18% | 旧数字冻结，后续只使用可追溯运行结果 |

## 3. 原 VHR-Opt 设计审计

### 3.1 可保留

- LLM 是生成器，verifier/evaluator 是裁判。
- 结构侧和解侧分开验证。
- 候选档案、搜索预算和 trace store。
- 小规模 oracle、传统 heuristic 与 LLM variants 的消融。
- verification 与 evaluation 分离。

### 3.2 必须修改

| 原设计 | 问题 | COVER-Opt 修改 |
|---|---|---|
| LLM 可生成完整方案或任意评分函数代码 | 生成空间太大，存在 heuristic trap 和安全问题 | 使用 typed DSL，禁止任意代码 |
| violation report 主要是自然语言 repair hint | 与通用反馈修复区别不够 | 构建 constraint-decision conflict graph |
| elite/diverse/repair queue | 已是常见搜索框架，创新不足 | 只作为控制器；核心变为 counterexample selection + targeted patch |
| 动态场景只是扰动 | 不能支撑动态部署主张 | 滚动时域、上一部署、迁移预算、失败回退 |
| IR 作为 Contribution 1 | NL-to-optimization 已有大量工作，原论文也已有 | IR 降级为基础设施与独立解析实验 |
| MCTS 作为进阶 | 实现成本高且不能自动形成新意 | 首版删除；只有档案搜索效果遇到明确瓶颈才重新评估 |

## 4. 近邻工作压力与差异边界

| 近邻工作 | 已覆盖机制 | 新版不能只声称 | COVER-Opt 的计划差异 |
|---|---|---|---|
| OptiMUS/OptLLM | LLM 建模、solver code、执行反馈 | 自动建模和代码自纠错 | 搜索受限部署算子，并定位失败决策 |
| OPRO/FunSearch/EoH | 评分反馈、程序空间搜索、启发式演化 | evaluator-guided search | Space-CPN typed DSL + conflict-targeted patch |
| Hercules | elite abstraction、性能预测、低成本启发式生成 | 精英摘要或性能预测 | 不以预测器为核心；使用确定性 conflict localization |
| FALCON | 语法约束、可行性修复、adaptive Best-of-N | structured output + repair | 部署/路由决策图到 DSL 组件的定向修复 |
| Formalize, Don't Optimize | 证明 raw heuristic generation 有长尾 correctness 风险 | LLM 任意生成更快 heuristic | 限制 DSL、独立静态验证、固定执行骨架 |
| DASH | dynamics-aware metric、profiled heuristic library | 动态感知或启发式库检索 | 动态作为目标场景；算法核心仍是冲突图反例修复 |
| CoEvo-AHD | 耦合子问题的双种群算子协同 | placement/routing 双算子演化 | 首版不做双种群，只做部署算子 + 确定性路径选择 |
| Space-CPN Robust RL | 鲁棒部署、请求不确定性、QoS | 首次动态/鲁棒 Space-CPN 部署 | 比较训练成本与重配置边界，不声称替代 RL 的鲁棒性 |

上述差异均为“计划中的方法边界”，不是已验证的新颖性结论。正式投稿前仍需按投稿截止时间再次检索。

## 5. 可行性审计

### 5.1 数据与场景

可行：原论文已有 Walker Delta、节点资源、微服务 DAG 和时延公式，可重建时间离散仿真。

缺口：原论文没有公开完整参数范围、随机种子和源代码。工程实现必须使用透明配置重新构建场景，并将“复现原趋势”与“精确复现原数值”区分开。

### 5.2 小规模 oracle

可行：将每时隙的节点间传输/传播时延预计算后，可以使用 OR-Tools CP-SAT 对小规模部署做 exact/near-exact 参照。大规模 oracle 不作为要求。

风险：联合多路径带宽和跨时隙迁移会快速扩大模型。首版先对静态小规模 placement + deterministic routing 计算 gap。

### 5.3 DSL 与执行骨架

可行：JSON AST、白名单特征与算子可由标准解析器安全执行，不需要运行模型生成代码。

风险：DSL 过窄可能压制 LLM 的探索价值。必须加入 `raw Python generation` 或较自由的 expression baseline，验证约束是否换来了可靠性而没有完全牺牲性能。

### 5.4 冲突图

可行：容量、资格、路径和迁移冲突可以精确关联到相关决策；QoS 冲突可以关联到关键路径上的 placement/route 决策。

风险：严格 minimal unsat core 对混合约束成本较高。首版实现 deterministic conflict attribution，不使用“最小冲突核”强表述。

### 5.5 LLM 搜索

已实现：LLM refinement 生成 DSL patch；可选初始化生成完整 typed DSL。两者均可缓存、可离线 replay，并经过静态验证和统一 evaluator。Mock/Replay 路径可在无 API 条件下完成机制测试。

风险：完整方法可能不优于人工启发式。该结果必须被允许出现；若没有稳定提升，论文贡献应转向可靠性、成本和错误分析，或重新评估方法。

补全后的实现边界：

- 反例必须在至少一次修复失败后才能进入重访调度，首次修复不再被误计为 replay。
- outcome-rejected 子候选仍保留于审计轨迹，但不得被选为后续父候选。
- `CounterexampleReplayCampaignRunner` 使用完整场景快照、反例、合格父 DSL 和来源运行启动新的求解运行，其落盘产物可区分 seed 与 scenario replay。
- typed multi-start 的初始生成与 refinement Patch 共享 `total_llm_calls` 上限，并分别记录 initial/patch 调用；失败调用同样计费。

上述是机制和可审计性证据，不是“replay 必然提高成功率”或“multi-start 必然提高解质量”的性能证据。

## 7. Go/No-Go 门禁

### Gate A：确定性内核可信

- verifier 在人工构造违规用例上逐类通过。
- 小规模随机实例中，verifier 与 CP-SAT 可行性判断一致。
- objective evaluator 对手算样例一致。

未通过：停止接 LLM，先修复仿真和约束实现。

### Gate B：表示可用

- 至少三个人工 DSL heuristic 能稳定运行。
- DSL 静态拒绝非法特征、无限值、过深表达式和非法 repair action。
- execution skeleton 在静态小规模场景产生可验证计划。

未通过：调整 DSL，不开始搜索实验。

### Gate C：反馈机制有效

- 冲突图在标注用例上能定位主要违规决策与相关 DSL 组件。
- targeted repair 相比 generic feedback 在固定调用预算下至少表现出稳定的修复率或调用效率优势；数值阈值在预实验后锁定。

未通过：Contribution 2 降级，不能用整体结果掩盖。

### Gate D：完整方法可写

- 多随机种子、静态和动态场景均完成。
- 主结果、消融、成本、错误分析和 negative cases 齐全。
- 所有结果可从 run manifest 追溯到配置、代码版本、模型和原始轨迹。

未通过：不更新简历为“已实现完整强化方法”。

## 8. 最终判断

`COVER-Opt` 比原 VHR-Opt 更值得实现，原因不是模块更多，而是研究问题更尖锐：它直接回答“如何在不训练 LLM 的前提下，避免任意启发式生成的正确性长尾，并利用约束反例定向改进部署规则”。

核心工程机制已经可运行，但该方法仍属于中等风险研究路线。离线控制测试只证明各开关改变了真实搜索路径；真正能否形成强论文贡献，仍取决于预算匹配的独立实验：冲突定向反馈与实际反例重放是否提高修复/搜索效率，typed DSL 与多起点是否在可靠性收益之外保持可接受的解质量。v1.3 的既有负结果不得被新机制实现本身覆盖。
